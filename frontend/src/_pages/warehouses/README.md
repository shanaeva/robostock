# ROBO-19: Мои склады

Команды ниже выполняются из корня pnpm workspace (где находится общий lock-файл).
Используйте Node из `.nvmrc` и pnpm из `packageManager`.

## Выбор источника данных

По умолчанию работает деморежим. Для явного выбора в `frontend/.env.local`:

```dotenv
NEXT_PUBLIC_WAREHOUSE_DATA_SOURCE=mock
```

Запуск: `pnpm --filter frontend dev`, затем открыть `/warehouses` на адресе,
который напечатал Next.js. Сервер API не нужен. Данные и QueryClient принадлежат
смонтированной странице; изменения хранятся в памяти и сбрасываются после перезагрузки.

После появления сервера задайте в том же локальном файле:

```dotenv
NEXT_PUBLIC_WAREHOUSE_DATA_SOURCE=http
NEXT_PUBLIC_API_BASE_URL=
```

Заполните вторую переменную фактическим HTTP(S) адресом API от бэкендера,
включая префикс API, если он есть. Адрес не содержит учётных данных, query или hash.
Слеш в конце необязателен. Адрес сервера сейчас неизвестен и в код не зашит.
Перезапустите dev-сервер; для production пересоберите frontend:
`NEXT_PUBLIC_*` подставляются Next.js в клиентскую сборку. Эти значения публичные,
секреты в них хранить нельзя. Названия переменных введены для этой страницы:
общего соглашения frontend пока нет.

HTTP-режим никогда не переключается на моки при ошибках. Неизвестный режим или
отсутствие адреса API показывают ошибку. `?demo=...` в HTTP-режиме игнорируется.
В интерфейсе HTTP-режима нет уведомления о демоданных и фильтра демонстрационных ролей.

Код складов находится в одном слайсе `src/_pages/warehouses`: `api` содержит
общий интерфейс `WarehouseDataSource`, два адаптера и запрос списка;
`model` — типы, схемы контракта и команды; `ui` — страницу, список и диалоги.
Отдельные слайсы сущности и действий не создаются, пока их использует только
эта страница. Маршрут Next.js импортирует страницу через публичный `index.ts`.

## Ручная проверка mock-режима

- `/warehouses` — четыре склада, обе роли, поиск совместно с фильтром.
- `/warehouses?demo=empty` — пустой список; создание первого склада работает.
- `/warehouses?demo=error` — первая загрузка завершается ошибкой; «Повторить» загружает список.
- `/warehouses?demo=mutation-error` — операции завершаются ошибкой; формы сохраняют значения, записи не удаляются.
- `/warehouses?demo=forbidden` — действия над существующими складами возвращают 403; создание собственного склада остаётся доступным.

Переходить между сценариями следует с полной перезагрузкой страницы.
Переключателей сценариев в обычном интерфейсе нет.

Проверить:

1. Открыть создание: ширина и высота по умолчанию 20 × 20 клеток.
2. Отправить пустое название, пробелы и название длиннее 100 символов: ошибка рядом с полем. Проверить границу в 100 символов после обрезки пробелов.
3. Для каждого размера проверить пустой ввод, 0, отрицательное число и дробь: ошибка рядом с соответствующим полем.
4. Создать склад с размерами, например, 32 × 12: название обрезается, размеры появляются в списке, роль — «Владелец». Снова открыть создание: новая форма показывает 20 × 20.
5. На `?demo=mutation-error` отправить название и размеры: после ошибки все введённые значения остаются в форме.
6. Переименовать склад: форма содержит только название, размеры после успеха не меняются. Отменить удаление, затем подтвердить удаление.
7. У наблюдателя нет действий изменения, удаления и приглашения; создание собственного склада доступно.
8. Приглашение: проверить email и увидеть подтверждение демо-сценария без обещания отправки письма.
9. Проверить Tab/Shift+Tab, Escape, начальный и возвращаемый фокус; при удалении начальный фокус — «Отмена».
10. Проверить ширины 320, 375, 768, 1024 и 1280 px: карточки / таблица, размеры складов и форма без горизонтального переполнения.

## Черновик OpenAPI 0.3.0-draft

Изучен приложенный `warehouse-editor.openapi.json`, версия `info.version` —
`0.3.0-draft`. Сервер не подключён: моки воспроизводят только описанные ниже
операции управления складами. HTTP-адаптер подготовлен, но интеграция
с настоящим сервером и авторизацией ещё не проверена.

| Операция       | HTTP                               | Ответ                          |
| -------------- | ---------------------------------- | ------------------------------ |
| Список         | `GET /warehouses`                  | `{ list, total, page, limit }` |
| Создание       | `POST /warehouses`                 | `201 { warehouseId }`          |
| Переименование | `PATCH /warehouses/{warehouseId}`  | `204`, без тела                |
| Удаление       | `DELETE /warehouses/{warehouseId}` | `204`, без тела                |

Пути приведены относительно адреса API. Для успешных переименования и удаления
тело не читается. Моки возвращают ту же обёртку списка и результаты операций.
Поиск `search`, `page`, `limit`, `sortBy` (`id/name/width/height`) и `sortOrder`
(`asc/desc`) передаются серверу и входят в ключ TanStack Query вместе с режимом.
В интерфейсе доступны размеры страницы 20, 50 и 100. Изменение поиска,
фильтра, сортировки или размера страницы возвращает на первую страницу.
После изменения данных список инвалидируется, затем открывается первая страница.
Мок применяет поиск, демонстрационный фильтр ролей и сортировку ко всему набору
до пагинации. HTTP-список локально не фильтруется: поиск относится ко всем
доступным записям на сервере, а не только к загруженной странице.

- Создание принимает `{ name, width, height }` и возвращает только `{ warehouseId }`.
- Название обрезается по краям и должно содержать от 1 до 100 символов.
- Ширина и высота — обязательные числовые целые значения не меньше 1. Верхний предел не добавлен. HTML-поля преобразуются в числа через React Hook Form `valueAsNumber`; пустой ввод не превращается в 0 и отклоняется валидацией.
- 20 × 20 — начальные значения формы по требованиям задачи. В черновике 20 указано как пример, а не как серверное значение по умолчанию.
- Переименование принимает ID и `{ name }`, не изменяет размеры и возвращает `undefined`, имитируя ответ 204 без тела. Удаление также возвращает `undefined`.
- После успешного создания, переименования или удаления TanStack Query перечитывает список. Объект склада из ответа операции не ожидается.
- Передаются только размеры склада: сетка и данные объектов карты не создаются.

## Допущения и интеграция

- `WarehouseSummary` и `WarehouseListDto` описывают только серверные данные. Модель отображения `Warehouse` допускает отсутствие роли; отдельная `DemoWarehouse` требует демонстрационный `currentUserRole`. В HTTP-ответе роль не читается, даже если сервер пришлёт несогласованное дополнительное поле.
- В HTTP-режиме показано «Роль не указана», изменение, удаление и приглашения скрыты. Их HTTP-методы подготовлены, но UI не разрешает действия владельца без подтверждённых прав. Создание остаётся доступным, API может отказать в нём с 401/403. Согласовать способ получения прав по каждому складу и, при необходимости, серверный фильтр ролей; не назначать всем Owner.
- Роли существующих тестовых складов сохраняются, новый склад только в mock-режиме получает Owner. Демороль и доступность кнопок не являются серверной защитой.
- Идентификаторы исходных демозаписей условные; у новых записей генерируется UUID. Серверная валидация ID не подключена.
- Уникальность названий не вводилась: в черновике такого требования нет.
- Приглашение по email с ролью Observer — демонстрационное допущение, в этом OpenAPI его нет. Почта, принятие приглашения и управление доступом не реализованы.
- OpenAPI описывает JWT в HttpOnly cookie `access_token`. HTTP-запросы используют `credentials: 'include'`; токены, вход и хранение пользователя не реализуются. Для запросов между разными origin сервер должен разрешать фактический origin frontend и credentials в CORS; cookie должны иметь подходящие настройки SameSite/Secure. Договориться с командой авторизации о локальном входе, истечении сессии, CSRF-защите и общем поведении 401/403.
- Ошибки `{ statusCode, message }` разбираются по контракту; для пустого, HTML или неожиданного тела используется понятное сообщение по HTTP-статусу. Ошибки сети обрабатываются отдельно. Для 401/403 показаны сообщения без перехода на выдуманную страницу входа. Успешные JSON-ответы проверяются Zod; некорректный ответ считается ошибкой. Повторы запросов и мутаций автоматически не выполняются; при ошибке загрузки есть «Повторить».
- Скрытие действий в UI не является защитой. Моки дополнительно проверяют роль и умеют возвращать 403; реальный API должен проверять права независимо.
- Маршрут экрана склада не согласован, поэтому «Открыть» недоступно.
- QueryClientProvider находится только в границах страницы. Корневой layout и конфигурация не меняются.
- Button, Input и Dialog адаптированы из shadcn/ui (MIT) без CLI init, глобальных CSS-токенов и анимационных зависимостей.

## Автоматические проверки

Во frontend нет отдельной конфигурации Vitest и RTL. Для тестов адаптеров
используется уже установленный в workspace Vitest из backend, без его конфигурации,
Prisma setup, установки зависимостей и изменений общих файлов:

```sh
pnpm --filter @starter/backend exec vitest run --root ../frontend
pnpm exec prettier --check frontend/src/_pages/warehouses
pnpm --filter frontend lint
pnpm --filter frontend exec tsc --noEmit --incremental false
```

`api/http-api.test.mjs` проверяет пагинацию/параметры, DTO без роли, создание,
ответы 204, ошибки API/сети, отсутствие отката к мокам и разделение режимов.
Это тесты с подменённым fetch, а не проверка работающего сервера.
RTL и среда браузерных компонентных тестов не устанавливались.

Для совместной проверки с бэкендером нужны адрес API, способ получить cookie,
пользователи с разными правами и склады на нескольких страницах. Проверить поиск,
сортировку, навигацию страниц, создание и сохранение после перезагрузки,
401/403/404, пустое и некорректное тело ошибки, недоступный сервер.
После согласования источника прав включить кнопки владельца и проверить
переименование/удаление, отмену удаления и прямой запрещённый запрос от наблюдателя.
Приглашения/принятие доступа требуют отдельного контракта. С командой карты
нужно согласовать маршрут «Открыть»; новый маршрут здесь не создаётся.
